# Как устроен Harness: полное описание пайплайна

Этот файл — подробное техническое описание того, как весь Harness работает изнутри: как
оркестратор строит план, как субагентам подбираются инструменты и скиллы, зачем нужен каждый
субагент, и как всё это в итоге превращается в отчёт. Короткая версия — в [README.md](README.md);
здесь — версия «для тех, кому интересно, что происходит под капотом».

## 1. Что решает система

По исследовательскому запросу пользователя (например, *«сравни MitoQ со стандартной терапией при
болезни Паркинсона»*) система:

1. находит свежие (по умолчанию — с 2021 года) публикации и регистрации исследований;
2. извлекает из них структурированные данные (препарат, мишень, фаза, размер выборки, исход,
   эффект);
3. перепроверяет каждую цитату по исходным API, чтобы отсеять галлюцинации;
4. считает агрегированную статистику и сравнивает митохондриально-таргетную терапию со
   стандартом лечения;
5. ранжирует направления по перспективности с явным обоснованием;
6. собирает итог: отчёт на бытовом языке + технический отчёт с графиками, таблицами и ссылками
   (PMID/DOI/NCT).

Это исследовательский инструмент экспресс-скрининга литературы, а не систематический обзор и не
медицинская рекомендация — это явно указано в каждом отчёте.

## 2. Общая схема

```
Запрос пользователя (+ заболевание, классы препаратов, год)
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│  ОРКЕСТРАТОР -- build_plan()                               │
│  · формирует user_prompt из запроса + области охвата       │
│  · вызывает LLM с METAPROMPT -> получает обоснование        │
│    (scope_notes + rationale на каждый шаг пайплайна)        │
│  · собирает Plan: 6 фиксированных шагов, каждый со своим    │
│    набором tools/skills (см. раздел 4)                       │
│  · план целиком логируется и уходит в UI                    │
└───────────────────────────────────────────────────────────┘
        │
        ▼ literature_searcher.run(plan)
        ▼ data_extractor.run(hits, diseases, drug_classes)
        ▼ reviewer_validator.run(studies)          -- фильтрует studies
        ▼ comparator_analyst.run(kept_studies, diseases)
        ▼ perspective_scorer.run(kept_studies, comparisons)
        │
        ▼
┌───────────────────────────────────────────────────────────┐
│  ОРКЕСТРАТОР -- сборка отчёта                               │
│  · _build_plain_summary(): пересказ выводов простыми        │
│    словами (без новых фактов -- только то, что уже посчитано)│
│  · _report_markdown(): технический отчёт (таблицы, графики, │
│    PMID/DOI/NCT, ограничения)                                │
│  · запись outputs/reports/*.md + outputs/logs/*.jsonl        │
└───────────────────────────────────────────────────────────┘
```

Порядок шагов — **поиск → извлечение → ревью → сравнение → оценка → отчёт** — сознательно
отличается от иллюстративного порядка в задании (*поиск → извлечение → сравнение → оценка →
визуализация → отчёт*): ревьюер-валидатор здесь идёт сразу после извлечения, а не в конце, чтобы
сравнение и рейтинг считались уже по проверенному по цитированию набору записей, а не строили
выводы на данных, факт-чек которых происходит только постфактум. Это решение само по себе
логируется как часть плана.

## 3. Оркестратор: как именно строится план

Функция `build_plan()` в [src/orchestrator.py](src/orchestrator.py) делает следующее:

1. Список шагов пайплайна **фиксирован в коде** (`_FIXED_STEPS`) — 6 шагов, каждый с заранее
   заданным субагентом и набором инструментов/скиллов (см. таблицу в разделе 4). Это осознанное
   архитектурное решение: пайплайн для этой предметной области всегда один и тот же (поиск →
   извлечение → ...), поэтому нет смысла просить LLM каждый раз изобретать шаги заново — это
   было бы источником нестабильности без реальной пользы.
2. То, что LLM **действительно решает** на этом шаге:
   - `scope_notes` — проверка, что запрос не выходит за рамки предметной области (митохондриальная
     медицина vs стандарт лечения; отказ от клинических рекомендаций конкретному пациенту, отказ
     от несвязанной фармакологии);
   - `step_rationale` — по 1-2 предложения **обоснования, зачем именно этот шаг нужен для этого
     конкретного запроса** (не общие слова, а привязка к сути запроса — это и есть то самое
     «качество метапромпта», которое проверяется в критериях оценки).
3. Результат собирается в объект `Plan` (Pydantic) и целиком логируется одним событием
   (`plan=plan.model_dump(...)`) — именно поэтому в UI можно развернуть «Полный план исследования»
   и увидеть все 6 шагов с их `tools`, `skills` и `rationale` сразу после построения плана.

## 4. Как подбираются skills и tools субагентам

Для этого прототипа привязка «шаг пайплайна → субагент → инструменты → скиллы» **фиксирована по
дизайну** (см. `_FIXED_STEPS`), а не выбирается LLM динамически каждый запрос — это сделано
специально, чтобы поведение было воспроизводимым и предсказуемым:

| Шаг | Субагент | Инструменты | Skills |
|---|---|---|---|
| search | `literature_searcher` | `pubmed.search_literature`, `clinicaltrials.search_trials` | — |
| extract | `data_extractor` | `structured_parse` (LLM + Pydantic-схема) | `clinical_outcome_extraction_rules`, `evidence_level_scale` |
| review | `reviewer_validator` | `verify_citation` | `citation_validation_checklist` |
| compare | `comparator_analyst` | `sandbox.compare_arms`, `sandbox.plot_effect_by_phase` | — |
| score | `perspective_scorer` | `sandbox.plot_ranking` | `perspective_criteria`, `evidence_level_scale` |
| report | `orchestrator` | — | — |

Что здесь по-настоящему «динамическое» (то, ради чего в задании и требуется **runtime-инъекция**,
а не хардкод промпта):

- **Skills подгружаются как файлы, а не встраиваются в код.** Функция `load_skills()` в
  [src/subagents/base.py](src/subagents/base.py) на каждом запуске читает `.md`-файлы из
  `/skills/*.md` с диска и подставляет их содержимое в системный промпт нужного субагента. Если
  отредактировать, например, `skills/perspective_criteria.md` (поменять веса критериев), поведение
  `perspective_scorer` изменится **без единой правки Python-кода** — это и есть «чистота
  runtime-инъекции» из критериев оценки.
- **Каждая загрузка скилла логируется отдельным событием** (`skill_loaded`) с полным текстом
  файла — в UI это разворачивается по клику, так видно, что реально было передано модели.
- **То, что субагенты делают внутри своей зоны ответственности, всё ещё решает LLM.** Например,
  `literature_searcher` не получает готовые поисковые запросы — он **сам формулирует** их (сколько
  запросов, какие термины, что покрыть для препарата, а что для стандарта лечения), основываясь на
  области охвата (заболевания/классы препаратов) из плана; фиксирован только сам факт, что этот шаг
  использует эти два инструмента.

## 5. Субагенты подробно

Каждый субагент — это отдельный модуль в [src/subagents/](src/subagents/), не класс, а набор
функций с общим шаблоном: `load_skills()` → системный промпт → `llm_call_json()` (или чистые
вызовы инструментов без LLM, где это уместно). Общая инфраструктура — в
[src/subagents/base.py](src/subagents/base.py).

### 5.1 `literature_searcher` — поисковик литературы

- **Роль:** превратить область запроса (заболевания, классы препаратов, окно дат) в конкретные
  поисковые запросы и получить сырые данные.
- **Как работает:** один вызов LLM (`search_strategy`) генерирует до 3 pubmed-запросов и до 2 пар
  condition/intervention для ClinicalTrials.gov **на каждое заболевание**, с явным требованием
  покрыть и митотерапию, и стандарт лечения (чтобы было с чем сравнивать), и писать запросы
  **по-английски** (даже если сам вопрос пользователя на русском) — потому что базы англоязычные.
- **Инструменты:** `pubmed.search_literature()` (Europe PMC REST API, без ключа) и
  `clinicaltrials.search_trials()` (ClinicalTrials.gov API v2).
- **Защитная логика:** модель иногда добавляет в запрос дату вида `2021/01/01[PDAT]` (синтаксис
  NCBI, а не Europe PMC), что тихо обнуляет результат — есть regex-очистка (`_strip_date_syntax`),
  которая вырезает такие вставки перед реальным запросом к API.
- **Выход:** список `SourceRecord` (заголовок, абстракт, PMID/DOI/NCT, год), дедуплицированный по
  идентификатору.

### 5.2 `data_extractor` — экстрактор данных

- **Роль:** превратить сырые хиты (абстракты/карточки исследований) в строго типизированные
  `StudyRecord` (Pydantic): препарат, мишень, заболевание, рука (`mitotherapy` /
  `standard_of_care` / `combination` / `placebo`), фаза, n, тип исследования, исход, направление
  эффекта, уровень доказательности.
- **Skills:** `clinical_outcome_extraction_rules.md` (как заполнять каждое поле, в т.ч. именное
  исключение — идебенон при LHON считается `standard_of_care`, а не `mitotherapy`, потому что это
  EMA-одобренный стандарт лечения именно для этого заболевания) и `evidence_level_scale.md` (шкала
  из 7 уровней доказательности, от РКИ двойное слепое до доклиники).
- **Батчинг:** хиты обрабатываются пачками по 6 за один вызов LLM — компромисс между вниманием к
  каждой записи и количеством вызовов/задержкой.
- **Защита от мусора на выходе:** каждая запись валидируется через Pydantic; если модель что-то
  испортила (например, вернула номер уровня доказательности вместо строкового названия — известная
  особенность модели), код нормализует то, что можно нормализовать (`_normalize_evidence_level`),
  а то, что нельзя — **отбрасывает и логирует как `issue`**, а не роняет весь прогон.
- **Выход:** список `StudyRecord`, один входной хит может дать несколько записей (если в абстракте
  несколько рук/препаратов).

### 5.3 `reviewer_validator` — ревьюер-валидатор

- **Роль:** отсечь галлюцинации до того, как они попадут в сравнение и рейтинг.
- **Как работает в два слоя:**
  1. **Детерминированная проверка (без LLM):** для каждой записи `verify_citation` повторно
     запрашивает исходный API по PMID/DOI/NCT (`pubmed.lookup_by_id` / `clinicaltrials.lookup_by_nct`)
     и сверяет похожесть заголовков (`difflib`). Если идентификатор не резолвится или заголовок не
     совпадает — это `unverifiable_citation`/`number_mismatch` высокой серьёзности.
  2. **Проверка через LLM** (skill `citation_validation_checklist.md`) — уже не про существование
     цитаты, а про содержательные вещи, которые код не может проверить формально: непроверяемые
     цифры, необоснованные превосходные формулировки («доказанно эффективен», «одобрен» без
     оснований), выход за пределы области заболевания/препарата.
- **Что происходит с найденными проблемами:** запись с замечанием высокой серьёзности **исключается**
  из дальнейшего анализа (сравнения и рейтинга), но не исчезает бесследно — попадает в раздел
  «Замечания валидатора» в отчёте вместе с причиной.
- **Выход:** отфильтрованный список `StudyRecord` + список `ReviewIssue`.

### 5.4 `comparator_analyst` — аналитик-сравнитель

- **Роль:** посчитать агрегаты и сравнить руки лечения по каждому заболеванию.
- **Числа считает не LLM, а чистый Python** (`src/tools/sandbox.py::compare_arms/arm_stats`):
  количество исследований, суммарная выборка, средний балл направления эффекта (ухудшение=-1 …
  улучшение=+1), микс уровней доказательности. LLM получает уже готовые числа и пишет **только**
  короткое текстовое пояснение (`summary`), с явным запретом «пересчитывать или противоречить» цифрам —
  это защита от того, чтобы модель считала статистику в уме и ошибалась.
- **Визуализация:** `sandbox.plot_effect_by_phase()` — scatter-график: фаза исследования (X) vs
  направление эффекта (Y, категориальная шкала), размер точки = размер выборки, цвет = рука.
- **Выход:** `ComparisonResult` на каждое заболевание + путь к PNG-графику.

### 5.5 `perspective_scorer` — оценщик перспективности

- **Роль:** ранжировать направления терапии (препарат × заболевание) по тому, насколько они
  перспективны, с воспроизводимым обоснованием.
- **Skills:** `perspective_criteria.md` — фиксированная взвешенная рубрика (сила доказательств
  40%, устойчивость/величина эффекта 25%, сигнал безопасности 15%, активность пайплайна 20%,
  плюс жёсткие ограничители — например, единственная маленькая серия случаев не может дать больше
  55 баллов, независимо от арифметики) и `evidence_level_scale.md`.
- **Группировка направлений:** по паре (препарат, заболевание), **регистронезависимо** — иначе
  «idebenone» и «Idebenone» из разных батчей экстракции превратились бы в два разных направления в
  рейтинге (реальный баг, найденный и исправленный в процессе разработки).
- **Визуализация:** `sandbox.plot_ranking()` — горизонтальный bar chart, отсортированный по баллу.
- **Выход:** список `PerspectiveScore` (ранг, балл, обоснование) + путь к PNG-графику.

## 6. Инструменты (tools)

Все инструменты — чистые функции без состояния в [src/tools/](src/tools/), вызываются напрямую из
кода субагентов (не через LLM function-calling — для этого прототипа это не понадобилось, LLM
готовит параметры, а Python сам делает HTTP-запрос/расчёт):

| Файл | Что делает |
|---|---|
| `pubmed.py` | Поиск (`search_literature`) и точечный lookup (`lookup_by_id`) через Europe PMC REST API — не требует ключа, возвращает PMID/DOI напрямую. |
| `clinicaltrials.py` | Поиск (`search_trials`) и lookup по NCT ID через ClinicalTrials.gov API v2. |
| `sandbox.py` | Вся арифметика (`compare_arms`, `arm_stats`) и все графики (`plot_effect_by_phase`, `plot_ranking`) на matplotlib — изолировано от LLM-кода намеренно. |
| `cache.py` | Дисковый кэш (`diskcache`) поверх HTTP-вызовов к PubMed/ClinicalTrials — бонусное требование задания, экономит повторные запросы при повторных прогонах одного и того же запроса. |

## 7. Логирование и трассировка

Всё проходит через единую шину событий — `EventBus` в
[src/logging_utils.py](src/logging_utils.py). У каждого события фиксированная структура
(`AgentEvent`): кто (`actor`), на каком шаге (`phase`), что произошло (`event_type`: start / tool_call
/ skill_loaded / llm_call / issue / end), человекочитаемое сообщение и произвольный `data` —
именно в `data` лежат полные промпты, полные ответы LLM, полные результаты поиска, полный план и
т.д. (по вашему запросу — см. раздел 8).

Каждое событие одновременно:
1. дописывается в `outputs/logs/<timestamp>_<slug>.jsonl` (один JSON-объект на строку — это и есть
   воспроизводимый лог делегирования/вызовов инструментов/скиллов из требований задания);
2. если передан колбэк `on_event` — уходит в него немедленно. Именно на этом построена live-трасса
   в Streamlit (`app.py`) и построчный вывод в консоли (`main.py`) — оба потребителя читают ровно
   один и тот же поток событий, просто по-разному его показывают.

## 8. Что именно видно в детальных логах UI

Поскольку изначально в трассе были только краткие однострочные сообщения, а затем это расширили до
полной прозрачности, сейчас у каждого типа события есть разворачиваемая деталь (см.
`_render_event_detail` в `app.py`):

- **`llm_call` (request)** — точный `system_prompt` и `user_prompt`, отправленные в модель (включая
  весь текст подгруженных скиллов внутри system_prompt).
- **`llm_call` (response)** — полный структурированный JSON-ответ модели.
- **`tool_call` с результатами поиска** — все найденные хиты (заголовок, PMID/DOI/NCT, год,
  абстракт, ссылка) в виде таблицы.
- **`tool_call` проверки цитаты** — что именно вернул повторный запрос к источнику (совпало ли
  название).
- **`skill_loaded`** — полный текст файла скилла.
- **план (`plan:end`)** — все 6 шагов целиком, с инструментами/скиллами/обоснованием.

## 9. Сборка отчёта: два слоя для разной аудитории

Финальный шаг оркестратора собирает `FinalReport` и рендерит его в двух слоях одного документа:

1. **«Простыми словами»** (`_build_plain_summary`) — отдельный вызов LLM, которому передаются
   **только уже посчитанные результаты** (сравнения, рейтинг, ограничения), а не сырые данные —
   поэтому он физически не может добавить новый факт или цифру, только пересказать то, что уже
   выведено и проверено остальным пайплайном, простым языком, без жаргона, с обязательным
   дисклеймером «это не медицинский совет».
2. **Технический отчёт** (`_report_markdown`) — обоснование плана, сравнение по заболеваниям с
   графиками (и пояснением «как читать график» под каждым), таблица рейтинга с графиком и полным
   обоснованием баллов, таблица доказательств с PMID/DOI/NCT-ссылками, ограничения и замечания
   валидатора.

Оба слоя идут в один файл `outputs/reports/<timestamp>_<slug>.md` — простое резюме сверху,
подробности ниже, ссылка друг на друга явно прописана в тексте.

## 10. UI (Streamlit, `app.py`)

- **Вкладка «Исследование»** — сайдбар (заболевание — одиночный выбор; классы препаратов —
  зависят от выбранного заболевания, см. `config.DISEASE_DRUG_CLASSES`; окно дат), поле запроса,
  живой индикатор «сейчас работает: <агент>», трасса по фазам (`st.status` на каждый шаг пайплайна)
  и итоговый отчёт (рейтинг + график, сравнения + графики с графиками-подсказками, таблица
  доказательств, замечания валидатора, скачивание `report.md`).
- **Вкладка «Архитектура»** — статичная схема: оркестратор → 5 субагентов по порядку выполнения →
  оркестратор (сборка отчёта), каждый субагент в своей карточке с ролью, инструментами и скиллами.

## 11. Локализация (`src/i18n.py`)

Внутренние данные (Pydantic-enum'ы `Arm`/`StudyType`/`EffectDirection`, английские названия
заболеваний и классов препаратов в `config.py`) намеренно остаются на английском — они участвуют в
сопоставлении с данными, извлечёнными из англоязычной литературы (например, фильтрация по
заболеванию идёт по строковому совпадению). `i18n.py` — это только слой отображения: словари
перевода на русский для UI, отчёта и подписей графиков, не затрагивающие сами данные.

## 12. Как это соотносится с критериями оценки в задании

| Критерий | Вес | Где это в коде |
|---|---|---|
| Архитектура Harness | 30% | Метапромпт + `build_plan()` с реальным обоснованием на каждый шаг; порядок ревью-до-сравнения как осознанное решение, а не копирование примера из задания. |
| Инструменты и Skills | 25% | 4 атомарных инструмента (>3 по заданию); skills — реальные `.md`-файлы, читаемые в runtime (`load_skills`), а не зашитый в промпт текст; минимум 2 skills по заданию — здесь 4. |
| Научная корректность | 30% | `reviewer_validator` с двойной проверкой (детерминированная + LLM); шкала доказательности; честное «нет данных» вместо натянутого вывода (см. `_report_markdown`, где при 0 исследованиях так и пишется). |
| Качество кода и визуализации | 15% | Числа и графики — чистый Python (`sandbox.py`), не LLM; понятные подписи графиков с пояснением, что означает каждая ось и размер маркера. |
